# EFMI 原生常驻方案实验说明

## 目标

本实验从未加入旧状态恢复代码的 v3.8.0 主线开始，验证一种不操作 `d3dx_user.ini` 的跨 Mod 状态方案：

- 需要切换的 Mod 始终由 EFMI 加载；
- 一个 EFMI 控制器使用 `global persist $active_profile` 记录当前方案；
- 各 Mod 的模型、纹理和快捷键入口受控制器变量约束；
- 每个 Mod 原有的 `global persist` 变量始终注册在 XXMI 中，由 XXMI 自己自动保存；
- 切换方案只改变 EFMI 内部变量，不要求 F10；
- 原始 Mod 永远不修改，只生成受控副本。

## 当前实现范围

v3.8.2 实验版已经实现：

1. 扫描配置方案引用的所有 Mod。
2. 识别标准 EFMI Tools 结构：`$mod_enabled`、`$object_detected` 和注册命令。
3. 检查 TextureOverride/ShaderOverride 是否存在无法确认的未门控运行效果。
4. 为标准运行条件和 Mod 快捷键加入控制器开关。
5. 将多个桌面配置方案生成为一个 EFMI `[Key] type = cycle` 方案控制器。
6. 把控制器和受控 Mod 副本生成到用户选择位置下的新文件夹。

当前版本不会直接部署到 `EFMI\Mods`，也不会删除、移动或覆盖真实 EFMI 文件。

## 使用方式

1. 为同一仓库建立两个或更多“配置方案”。
2. 每个配置方案保存希望同时启用的 Mod 组合。
3. 打开“Mod 更新”页面。
4. 在“EFMI 原生常驻方案（实验）”中先执行兼容性分析。
5. 只有全部 Mod 都显示为支持时，才能生成到独立文件夹。

生成后的默认游戏内按键为：

- `Ctrl + Right`：下一个方案；
- `Ctrl + Left`：上一个方案。

## 安全边界

- 不读取或写入 `d3dx_user.ini`。
- 不调用游戏进程内存接口。
- 不模拟 F10。
- 不修改 Mod 仓库中的源文件。
- 不自动写入真实 EFMI 目录。
- 输出位置已存在且非空时拒绝覆盖。
- 非标准 Mod 或无法证明完整门控的 Mod 拒绝自动生成。
