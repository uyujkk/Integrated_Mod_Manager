# 跨 Mod 内部状态保存：试验路线与当前结论

[文档索引 / Documentation Index](../README.md)

本文整理基于 v3.8.0 原始软件进行的跨 Mod 内部状态保存试验，并说明 v3.8.5 的实际支持边界。

> **当前结论：对任意第三方 XXMI / EFMI Mod 的 `$变量` 进行通用、自动、可靠的跨 Mod 保存与恢复，现阶段暂时无法实现。**
>
> v3.8.5 没有发布游戏内存注入、进程内存读写、自动按键或通用 `$变量` 恢复功能。发布版保留原有复制模式，并提供可选的目录联接部署；目录联接只能让 Mod 文件夹内部的文件写入直接回到仓库。

## 原始目标

管理器需要为每个 Mod 分别记住服装部件、颜色、变体和其他内部选项，并在切回该 Mod 或应用组合方案时恢复这些状态。难点在于不同 Mod 的变量名、命名空间、持久化方式和重载时序均不统一，部分状态只存在于游戏运行内存中。

## 为什么不能把 `d3dx_user.ini` 当成稳定接口

1. `d3dx_user.ini` 通常是多个 Mod 和加载器共享的全局文件，不是单个 Mod 的独立状态文件。
2. 游戏运行时，EFMI/3DMigoto 可能先将内存中的旧值写回磁盘，再执行配置重载；外部刚写入的值可能被立即覆盖。
3. 同名变量可能依赖 Mod 命名空间、注册时机和加载顺序。管理器不能仅凭文件夹名可靠推断这些关系。
4. 部分状态没有声明为 `global persist`，或使用字符串、向量、命令链和运行期计算，无法从一个通用文件格式完整恢复。
5. F10 是加载器级保存/重载动作，不是面向管理器的逐 Mod 状态恢复 API；不同分支的行为也可能不同。

## v3.8.5 可用方案的边界

目录联接部署解决的是原复制模式的“深拷贝”问题：加载器写入被链接 Mod 目录中的文件时，实际修改的就是仓库中的原文件。因此，切换到其他 Mod 再切回来，Mod 自己写入其目录的配置可以继续保留。

它不等于通用的游戏内状态保存：

- 能保留：Mod 自己目录内实际落盘的配置、缓存或状态文件。
- 不能保证：EFMI 根目录 `d3dx_user.ini` 中的 `global persist` 值。
- 无法处理：只存在于游戏进程内存、没有写入任何文件的临时状态。
- 不会执行：内存扫描、内存写入、DLL 注入、自动 F10 或反作弊绕过。

同一角色目录链接另一个 Mod 时，v3.8.5 会先安全断开该角色原有的受管目录联接，再创建新联接；普通复制目录和其他角色不会被自动删除。

## 重新评估该功能所需条件

只有在下列条件至少得到稳定满足后，才适合重新开发通用跨 Mod 内部状态恢复：

1. XXMI/EFMI 提供并文档化逐 Mod 状态的序列化、读取和恢复接口。
2. 存在稳定的 Mod 标识与变量命名空间映射，不需要猜测第三方 INI 结构。
3. 明确支持运行中重新读取外部状态，并规定保存、卸载、注册和恢复顺序。
4. 状态可以按 Mod 隔离和事务化恢复，而不是覆盖整份共享 `d3dx_user.ini`。
5. 能在真实游戏环境中验证兼容性、性能、失败回滚和账号风险边界。

在这些条件满足前，本项目会把 v3.8.1/v3.8.2 保留为研究记录，不把它们包装成可用功能，也不承诺任意 Mod 的内部 `$变量` 可以自动恢复。
